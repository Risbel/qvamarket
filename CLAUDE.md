# QvaShop — Project Context

This file gives full context to anyone (human or AI assistant) working on this repo.
Keep it updated: tick roadmap boxes and add decisions as they happen.

## What we're building

QvaShop is a **B2B2C multi-tenant SaaS** for creating online stores.

- I (the platform owner) sell the platform to businesses.
- A **company** (tenant) can own **several stores**.
- Each store lives on a subdomain: `https://<store-slug>.qvashop.com`.
- Merchants customize their store visually, publish products, receive **orders**, and manage fulfillment (pickup or home delivery).
- In the MVP, the superadmin (me) can do everything on behalf of a merchant, including creating their account.
- **No online payments in the MVP.** Payment is settled between merchant and customer outside the platform (cash, transfer, etc.); the merchant records it manually on the order.

**MVP goal:** 3–5 real merchants selling. Nothing else matters until that happens.

## Domains and routing

| Host | Purpose |
|---|---|
| `qvashop.com` | Marketing / landing |
| `app.qvashop.com` | Merchant panel |
| `admin.qvashop.com` | Superadmin panel |
| `<slug>.qvashop.com` | Public storefront |

- `proxy.ts` (Next.js 16; was `middleware.ts` before) reads the `host` header, resolves the store by slug, and rewrites internally. It also handles locale routing via next-intl.
- **Reserved slugs** that merchants cannot use: `www`, `app`, `admin`, `api`, `mail`, `static`, `assets`, `status`, `help`, `docs`.
- `ROOT_DOMAIN` env var (hostname only): `localhost` in dev, `qvashop.com` in prod. `src/lib/tenancy.ts` extracts the store slug from the host and holds the reserved slugs.
- Store hosts are rewritten to the internal route `/[locale]/stores/[slug]/...` (direct access to `/stores/...` on other hosts returns 404). The storefront page resolves the slug against the `store` table (`getPublicStoreBySlug`): unknown or inactive stores return 404 (so `prueba.qvashop.com` needs a store with slug `prueba`, created from the admin panel). `app.` / `admin.` hosts are not routed separately yet.
- Local development: use `*.localhost` (e.g. `http://mitienda.localhost:3000`), which resolves to 127.0.0.1 in modern browsers without editing the hosts file.

## Architecture decisions

### Multi-tenancy
- **One shared PostgreSQL database** for the MVP. Every tenant-owned table has a `tenant_id` column.
- Data model: **Company (tenant) → Stores → Products / Orders**. The company is the unit of isolation and billing; the store is the unit of catalog and branding.
- All IDs are **UUIDs (v7 preferred)**, never auto-increment, so a tenant's data can later be copied to another database without collisions.
- **Dates and times (decided 2026-10, migration `0012`):** every app timestamp is **`timestamptz`** (`timestamp(..., { withTimezone: true })`): an absolute instant, stored in UTC, independent of the database server's timezone. **Formatting happens in the viewer's browser** (`<LocalDateTime>`), so a customer abroad and the merchant each see the same purchase in their own local time. Never format a date on the server for display (the server does not know the viewer's zone). Better Auth's generated tables still use `timestamp` without zone (written from JS dates, UTC); leave them. `0012` is hand-edited (`USING <col> AT TIME ZONE 'UTC'`).
- **Filtering by day** uses the viewer's timezone too (`src/lib/date-range.ts`): the URL carries local dates plus the browser's IANA zone (`?from=2026-10-01&to=2026-10-07&tz=America/Havana`, validated with `parseDateRange`), and the query compares the instant's **local date** in that zone (`(created_at at time zone tz)::date between from and to`), plus wider instant bounds for the index. Do not convert a local midnight to an instant: some zones change clocks at midnight (Cuba's Nov 1 has 00:00 twice), so that boundary is ambiguous.
- **A company (tenant) is a Better Auth `organization`** (plugin enabled in `apps/web/src/lib/auth.ts`). `tenant_id` on any table = `organization.id`; merchant users are `member`s of it. No separate `companies` table.
- App tables live in `packages/db/src/app-schema.ts` (auth tables stay in the generated `auth-schema.ts`). Done so far: `store` (`tenant_id`, globally unique `slug` with a DB format check, `name`, `currency`, `status`, branding: `logo_key`, `logotype_key`, `primary_color`, `accent_color`). The `invitation` table exists because the plugin requires it but is unused (no email in the MVP).
- **Catalog v2 (decided 2026-10, migrations `0008`–`0010`)** — modeled after Shopify/Medusa/Saleor:
  - `currency` (platform table, seeded from `Intl.supportedValuesOf("currency")`: code PK, name, `digits`, `is_active`) and `store_currency` (which currencies a store sells in, `is_default` = exactly one, `is_base` = exactly one, `exchange_rate`, `rounding_minor`, `position`; see Exchange rates). `store.currency` no longer exists. `setStoreCurrencies()` refuses to remove a currency that still has prices (`inUse`).
  - `category`: one optional category per product (`product.category_id`, FK `ON DELETE SET NULL ("category_id")` so `tenant_id` is kept), `slug` unique per store (the storefront `#anchor`), **generated from the name, never typed by the merchant** (`categorySlug()` in `src/lib/slug.ts`: `-2`, `-3`... when taken, `categoria` for a name without letters or digits; regenerated on rename; computed under a store-row lock so concurrent saves cannot clash; the form previews it with the same function), `position`, `is_visible`, meta fields, `parent_id` reserved (UI is flat).
  - `product`: no price or stock any more; `slug` (unique per store, URL `/products/<slug>`, old id URLs redirect permanently), `tags text[]` (GIN), `meta_title`, `meta_description`.
  - **Variants:** `product_option`, `product_option_value`, `product_variant` (`sku` unique per tenant, `stock` null = not tracked, `weight_grams`, `option_key`), `variant_option_value`. **Every product has exactly one hidden default variant** (`is_default`, empty `option_key`) when it has no visible variants, so price, stock, cart and orders always work on variants (one code path). The cart stores `{ variantId, quantity }`. A product **with options** has no default variant: one variant per combination of option values (`option_key` = sorted value ids), max 3 options x 20 values and **50 combinations**.
  - **Editing options regenerates variants** (`setProductOptions` in `src/server/variants.ts`, planned by the pure, unit-tested `planVariants` in `src/lib/variant-plan.ts`): same combination -> the variant stays (renaming a value keeps its id, so its variant); otherwise a variant moves to the first free combination that contains all its values or vice versa (adding an option moves "M" to "M / <first value>", removing one keeps the first variant of each remaining combination, the default variant of a simple product becomes the first combination). Remaining combinations get new variants that **copy the regular prices of the first kept variant and start with stock 0** if it tracked stock (untracked otherwise), so nothing is oversold; leftover variants are deleted (carts holding them show "unavailable"). Removing all options makes the product simple again (the first variant becomes the default one). Option/value renames go through temporary names so swaps never trip the unique constraints. Writes lock the product row (`SELECT ... FOR UPDATE`), so concurrent saves are serialized; ids sent by the browser that are not the product's answer `stale`.
  - **Prices:** `variant_price` (`currency_code`, `min_quantity` ≥ 1 for volume tiers, `amount_minor` **bigint**, `compare_at_minor` > amount = strike-through price, `price_list_id` null = regular price). `price_list` (`kind` sale | override, `status` draft | active, `starts_at`/`ends_at`) holds dated promotions. Resolution in `src/lib/pricing.ts` (`resolvePrice`, unit tested): the regular row with the highest `min_quantity` ≤ qty; an active in-date `sale` applies only if cheaper, an `override` always. **Automatic prices through exchange rates** (see Exchange rates): a product is sold in a currency where it has a regular price at qty 1 of its own (manual) or, when that currency has a rate, through its base-currency price; otherwise it is hidden in that currency.
  - `store` profile columns: `description`, `phone`, `whatsapp`, `contact_email`, `address`, `pickup_instructions`, `opening_hours` (jsonb, no UI yet), `meta_title`, `meta_description`.
  - `product_image` unchanged (`storage_key`, `content_type`, `size_bytes`, `position` 0 = main image).
  - Hand edits in generated migrations: `0008` (unique constraint moved before the composite FKs that need it, column-list `SET NULL`, currency seed + data backfill), `0010` (hand-written: `variant_price_store_currency_fk` is `DEFERRABLE INITIALLY DEFERRED`, otherwise deleting a store/company with prices fails mid-cascade; drizzle-kit cannot express it).
- **Cross-tenant integrity is enforced by the database:** children carry `tenant_id` plus a **composite FK** to the parent's `(id, tenant_id)` (or `(id, store_id, tenant_id)` for variants and prices), so a row can never point at another tenant's parent. Do the same for every new tenant-owned table. Deleting a store/product cascades to rows only: **the code must also `deleteObject()` the image files**.
- **Drizzle gotcha:** inside a raw `sql` subquery in a *single-table* select, `${table.column}` can be rendered without the table name and silently bind to the subquery's table (this made every category count 0). Use a join + `groupBy`, or only use correlated subqueries in queries that already join.
- **Merchant panel** (`/[locale]/dashboard/...`, path-based for now; it moves to `app.` later): `dashboard/layout.tsx` and `admin/layout.tsx` both use `<PanelShell>` (`src/components/panel-shell.tsx`): the shadcn **sidebar** (`panel-sidebar.tsx`: brand header, nav groups with icons, "View store", account menu with change password / sign out; collapses to icons, state kept in the `sidebar_state` cookie so it renders collapsed on the server; a sheet on phones that closes when a link is followed), a page header with the toggle and the current section's name, and the banners (impersonation, store status). The nav items are computed on the server from permissions and passed as `groups`; a new section = an entry in `ITEMS` (`panel-sidebar.tsx`) + `Panel.nav.<key>` messages. The shell's `SidebarInset` is the page's `<main>`, so pages inside the panels render a `<div>`. While impersonating, the account menu is replaced by plain text (no sign out / password change). **Every merchant page and Server Action starts with `requireMerchant(locale)`** (`src/server/tenant.ts`: signed in + past the forced password change + member of a company with a store, else 404) and passes the returned `tenantId` / `store.id` to the query helpers in `src/server/*.ts` (e.g. `products.ts`), which always filter by `tenant_id`. Never take a tenant or store id from client input. The active company is chosen with the company switcher (see Roles and permissions); within it, the active store is the company's oldest store (no store switcher yet). `requireMerchant()` returns `store.currencies` and `store.defaultCurrency`; prices are shown with `formatMoney(minor, currencyCode, locale)` (`src/lib/money.ts`) or `<PriceTag>` (strike-through compare-at).
- **Products (merchant panel):** pages `/dashboard/products`, `/new`, `/[id]/edit`; the list (`products-table.tsx`, client) sorts in the browser by name, category, price, stock and status (no sort = server order, newest first; empty values last; names compared with `Intl.Collator`, so accents and case are ignored) and has a `...` menu per row (edit, view in store when the product and store are active, delete with confirmation); form = react-hook-form + zod (`createProductSchema(t, currencies)` in `lib/validation/product.ts`): name, description, category, status, **the base currency's price card** (price required, optional compare-at, up to 5 volume tiers) and a closed section "Prices in other currencies" (`VariantPrices` in `price-fields.tsx`: per currency "≈ amount" following the rate, or a "Manual price" switch that shows the same card, prefilled with the automatic price; switching back shows "7 500 → 8 000" and saving removes the manual rows; the section opens by itself when a currency is manual or has errors), SKU, stock, SEO (slug auto-filled from the name, tags, meta title/description). Prices are decimal strings converted to minor units on the server with `toProductInput()` / `parsePriceToMinor()` (string arithmetic, no floats); `form-values.ts` maps saved rows back. Empty stock = not tracked (null). For a product with options the form shows only the product's own fields (`createProductSchema(..., { simple: false })`, the server checks `productHasOptions` and ignores price/stock input); below it, the **options editor** (`options-editor.tsx`: names + value chips, Enter adds a value, live combination count) and the **variants editor** (`variants-editor.tsx`: one collapsible card per variant with SKU, stock and the same per-currency price fields as the product form — shared in `price-fields.tsx`; cards with errors open by themselves; `saveVariants` requires exactly the current variants, reports SKUs taken by other products per row). Both actions live in `src/server/variant-actions.ts` and need `product:update`.
- **Categories** (`/dashboard/categories`, `category:read`; create / edit / delete controls per permission): create (only a name; the #identifier is generated), rename, show/hide, move up/down, delete (its products stay, without category). **Settings** (`store:read` opens them read-only, saving needs `store:update`; decided 2026-10): **one route per section** under `/dashboard/settings/<section>` (not `?tab=`), so each page loads only its own data and checks its own permission; `settings/layout.tsx` renders the section menu (`settings-nav.tsx`: a horizontally scrolling row on phones, a vertical list from `md` up) and `/dashboard/settings` redirects to `general`. Sections: `general` (public profile: description, contact, address, SEO, and the **country for phone numbers**), `branding` (logo + colors), `banner` (storefront hero images for desktop and mobile, see Store banner), `currencies` (add, remove, choose the default), `pickup` (pickup instructions), `delivery`, `footer` (see Store footer), `pages` (see Custom pages). A new section = an entry in `SECTIONS` (`settings-nav.tsx`) + `Settings.nav.<key>` messages + its page (which calls `requireMerchantPermission` itself; the layout check alone is not enough). Add `delivery` in Phase 5; no placeholder pages for future sections. Categories and settings use `src/server/catalog-actions.ts` (same `getMerchantOrNull` + `can()` + re-validation pattern).
- **Promotions** (`/dashboard/promotions`, `/new`, `/[id]`; permission `promotion`: owner/manager edit, staff read; decided 2026-10): a promotion is a `price_list` with a name, kind (`sale` = the regular price is shown struck through and it only applies while cheaper, so the form and `savePromotion` reject sale prices >= the regular price; `override` = a special price that replaces the regular one, may be higher), on/off (`status` active | draft) and optional start/end dates. Its prices are `variant_price` rows with `price_list_id` and `min_quantity` 1, one per variant and currency (only currencies where the variant is sold). Outside the base currency an empty promotion price follows the base promotion price through the rate; the "% off" helper fills only the base and currencies with manual regular prices. The list shows the derived state (`promotionState()` in `src/lib/promotions.ts`: draft / scheduled / running / ended, same rule as `loadPriceRows`), quick activate/pause and delete (regular prices untouched). The form adds whole products (all variants), shows each regular price, and has a "% off -> apply to all" helper (`percentOff`). **Dates are entered and shown in the merchant's browser timezone** (`<DateTimePicker>`: a calendar day + a time, picking a day first sets 00:00 for the start and 23:59 for the end; converted to ISO/UTC before sending, `<LocalDateTime>` renders after hydration); stores have no timezone setting yet. Several running promotions on one variant: the cheapest price wins. Archived products already in a promotion keep their rows; only draft/active products can be added.
- **Storefront catalog:** category index (`category-index.tsx`: `#<category-slug>` anchors, merchant order, hidden categories excluded; uncategorized products go to `#_otros`) pinned **right under the header, above the banners**, full width; it slides away while scrolling down and comes back on any scroll up (same hook as the phone search row, `use-hide-on-scroll.ts`); a click on a link calls `holdBars()` so the bars stay shown through the jump and the heading lands under them (section `scroll-mt` counts header + search row + `--store-index`), sale / sold-out badges, volume tiers on the product page. **Product cards** (`product-card.tsx`, shadcn `Card`, image filling the top): the **image** (a link out of the tab order, `aria-hidden`) and the **eye button** (bottom right of the image, same look as the heart) open the product; the heart and eye are siblings of the image link, and the call to action (`product-card-actions.tsx`) **adds 1 unit straight to the cart** when exactly one variant is sold in the shopper's currency (`PublicListItem.quickAdd`), otherwise it links to the product page ("Choose options"); sold out = disabled. Hovering the image zooms it slightly (only the main image is loaded). **Variant picker** (`variant-purchase.tsx`): one row of buttons per option; the first buyable variant is preselected; choosing a value picks the exact combination or the best variant with that value; values whose combination is sold out are struck through, values with no price in the shopper's currency are disabled; `?variant=<id>` (kept in the URL with `history.replaceState`) preselects a variant for shared links. **Related products** under the product page (`listRelatedProducts` in `public-catalog.ts`, max 5, `RELATED_PRODUCTS_MAX`; compact `<ProductCard size="sm">`, 5 per row from `lg`, 2 / 4 below it, where the 5th is hidden): same category first, then more shared tags (accents/case ignored), then the newest others so the row stays full; sold-out last, products not sold in the shopper's currency left out; ranked in the app like the search. **Shopper currency** = host-only cookie `qvashop_currency` set by `<CurrencySwitcher>` (only shown with 2+ currencies) and validated on the server (`selectedCurrency()` in `src/server/storefront-currency.ts`); **without that cookie the default follows the visitor's country** (`currencyForCountry`: Cloudflare's `cf-ipcountry` header, `DEV_VISITOR_COUNTRY` in dev): Cuba -> CUP, euro countries -> EUR (else USD), elsewhere -> USD (else EUR), only among the store's currencies, otherwise the store default. It is not saved, so only the shopper's own pick sticks (a Cuban on a VPN gets the VPN country's currency and can switch); the server prices everything, including the cart (`priceCart`, tiers applied per quantity). Checkout must re-price the same way. **Server Actions** (`src/server/product-actions.ts`) use `getMerchantOrNull()` (never throws/redirects), answer `forbidden` when `can({ product: [...] })` is false, re-validate with the same schema, and call tenant-scoped helpers in `src/server/products.ts` (update/delete match `id` AND `tenant_id` AND `store_id`; another company's id is a 404/`notFound`). `deleteProduct` removes the rows and then the image files from storage.
- Every query must be scoped by tenant. Never write a query on tenant data without a `tenant_id` filter.
- Future (not MVP): Postgres Row Level Security, and a tenant registry with a per-tenant connection string so large tenants can be moved to a dedicated database.

### Auth and accounts
- Passwords are **hashed** by Better Auth. Never store plaintext or reversibly encrypted passwords.
- The superadmin creates merchant accounts with a temporary password and a `mustChangePassword` flag; the merchant must change it on first login. The flag is a Better Auth additional field (`input: false`, so users cannot set it) and is cleared server-side after the password change.
- **Forced password change:** while `mustChangePassword` is true, `requireUser()` (`src/server/session.ts`) and `requireAdminPage()` redirect to `/[locale]/change-password`, and `getAdminSession()` refuses the session. **Every protected page/layout must use `requireUser()` or `requireAdminPage()`** so the change cannot be skipped. `changePasswordAction` verifies the current password through Better Auth, revokes other sessions, then clears the flag.
- **Password reset (MVP recovery):** `resetMerchantPassword()` (button + dialog in the admin list) sets `mustChangePassword` first, then a new temporary password, then revokes all of the merchant's sessions; the credentials are shown once and forgotten when the dialog closes. It refuses admin accounts (`notFound`), so a superadmin password can never be reset this way.
- **Impersonation:** `startImpersonation(userId, tenantId)` / `stopImpersonation()` (`src/server/impersonation.ts`; in the admin list, **"Sign in as" is a menu with every member of that store's company** (name, role, email; admin and banned accounts excluded), and a banner on the merchant dashboard). The target must be a member of that company; the impersonated session opens **that company** (its `active_organization_id`), even if the person works in several. Every start/stop is a row in `impersonation_log` (admin, target, tenant, IP, user agent; emails snapshotted, FKs `SET NULL` so the trail survives deletions). The log row is written **before** the session is created and removed if that fails, so an unlogged impersonation cannot exist. Admin accounts cannot be impersonated; an impersonated session is a normal merchant session (`/admin` returns 404), so impersonations cannot be nested; sessions last 30 min. While impersonating, the forced password change is skipped (both `requireUser` and `requireAdminPage` check `session.impersonatedBy`). **Every signed-in layout must render `<ImpersonationBanner>` when `session.session.impersonatedBy` is set** (only the dashboard does so far; the merchant panel layout must too).
- **Rate limiting:** Better Auth limits `/sign-in/email` to 3 requests per 10 s per IP in production builds (the window resets after 10 s without requests); the login form shows a specific message on 429. **Deploy note:** behind Cloudflare + Traefik set `advanced.ipAddress.ipAddressHeaders: ["cf-connecting-ip"]` in `auth.ts`, otherwise all visitors share one counter.
- Superadmin logic lives in `apps/web/src/server/`: `getAdminSession(headers)` (role `admin`, not banned — every superadmin action must call it first), `createMerchant()` (user + company/organization with the user as owner + first store; compensates by deleting created rows if a step fails), `generateTemporaryPassword()`. Merchant users have role `user`; only the superadmin has role `admin`.
- Superadmin UI (path-based for now; the `admin.` host is not routed separately yet): `/[locale]/admin` (all stores with company + owner) and `/[locale]/admin/merchants/new` (create merchant form + one-time credentials card). `requireAdminPage()` guards the layout (anonymous -> login, non-admin -> 404); `createMerchantAction` re-validates and re-checks the admin role on the server.
- Password recovery in the MVP: the superadmin resets it manually. No email provider.
- Config lives in `apps/web/src/lib/auth.ts` (email+password, `admin` and `organization` plugins). **The base URL is resolved per request** (`baseURL: { allowedHosts }`): the `BETTER_AUTH_URL` host, `ROOT_DOMAIN` and `*.ROOT_DOMAIN` (with `BETTER_AUTH_URL`'s port, e.g. `*.localhost:3000` in dev); those hosts are also the trusted origins, so auth works on every store subdomain. A host outside the list falls back to `BETTER_AUTH_URL`.
- **The public sign-up endpoint is disabled** (`disabledPaths: ["/sign-up/email"]`, it answers 404): accounts are only created by our server code (`auth.api.signUpEmail` from merchant signup and customer signup, the superadmin's `createUser`), which applies the rate limits and creates the matching records. `disabledPaths` only affects HTTP requests, not `auth.api` calls.
- Auth tables live in `packages/db/src/auth-schema.ts`, **generated** by the Better Auth CLI (do not hand-edit; regenerate after changing plugins/config). IDs are UUIDs generated by PostgreSQL (`gen_random_uuid()`, v4 — PG 17 has no native v7).
- Create the first superadmin with the CLI (see Useful commands). Pages: `/[locale]/login`, `/[locale]/change-password`, `/[locale]/dashboard` (merchant panel), `/[locale]/admin` (superadmin).

### Roles and permissions (decided 2026-10)
- **Three kinds of identity, one global Better Auth `user` table:**
  1. **Superadmin** (platform role `admin`, admin plugin): only the owner of the platform. Not tenant data.
  2. **Merchant team** (company role via the `organization` plugin): the built-in `owner` (everything) plus the **company's own roles** (`company_role`, see below).
  3. **Customers**: no company membership; a `customer` record per company (see below). A customer can never open the merchant panel or the admin panel (both require membership / role).
- **Permissions are resource + action pairs**, defined once in `src/lib/permissions.ts` (pure, client-safe; no Better Auth import): `store` (read, update), `product` / `category` / `promotion` (read, create, update, delete), `order` (read, update = move the status forward, **cancel**), `payment` (read, create, delete: manual payments/refunds), `team` (read, create, update, delete), `role` (read, create, update, delete). `normalizePermissions` drops unknown entries and makes every write action bring `read`; `hasPermissions(granted, request)` = every requested action is granted. Adding a feature = adding its resource/actions there, granting them in the presets that should have them, and the `Roles.resources.*` messages.
- **Company roles (decided 2026-10, migration `0029`): our own table, not Better Auth's dynamic access control** (that one stores permissions as a text string in a generated table and exposes `/organization/*-role` endpoints). `company_role` (`tenant_id`, `key`, `name` unique per company ignoring case, `description`, `permissions` jsonb object, `preset_key`): `member.role` holds the role's **key** (a preset key like `manager`, or `r-<random>` for custom roles; it never changes on rename; `owner` is never a row, DB CHECK). Several keys comma-separated = the union. An unknown or deleted key grants nothing. Permissions are re-checked on read (`normalizePermissions`).
- **Presets** (`ROLE_PRESETS`, names in `Roles.presets.*`): `manager` (everything but team/role management; sees the team), `cashier` (orders incl. cancel, take payments, read catalog/store), `catalog` (products, categories, promotions), `dispatch` (orders read/update, payments read), `viewer` (read only). `ensureCompanyRoles(tenantId, locale)` (`src/server/company-roles.ts`) seeds them as **editable copies** into a company **that has no roles yet**: every new company (`createCompanyAndStore`) and, on first visit of the roles page, older companies. - **Pages and Server Actions check permissions, not role names:** pages call `notFound()` and actions return `forbidden` when `can()` is false. Never write `role === "owner"` in feature code (use `isOwner()` only in team management).
- **Client side** (`src/components/permissions/`): `<PermissionsProvider>` (in `dashboard/layout.tsx`, value = the server-resolved permissions), `useCan()` / `usePermission(request)`, `<Can permission fallback>` (hides, or `{(allowed) => ...}` to render disabled), `<PermissionTooltip allowed>` (explains a disabled control), `<PermissionFieldset permission>` (a native `<fieldset disabled>` + read-only notice around a whole form). **UX only: hiding is not authorization**, every action re-checks on the server. Server components use `merchant.can()`.

The temporary password is shown **once** (`credentials-panel.tsx`) and forgotten when the dialog closes. **An email that already has an account is refused** (`emailTaken`): an existing account (maybe a customer's) is never attached to a company without its owner's consent. Row `...` menu (`member-row-actions.tsx`): change role and reset password (`team:update`), remove (`team:delete`). **Rules, all in `team.ts`:** nobody acts on themselves (`self`) or on an owner (`owner`; the owner role is never given or taken here), nor on a member whose permissions exceed their own, nor gives a role granting more than their own (`escalation`); only this company's roles (`roleNotFound`); a superadmin account is a 404. The list shows "Also works in other companies" (never which). **Remove** deletes the membership only: **no session is ended** (membership is checked on every request, so this company's panel closes at once while the person stays signed in for their other companies and stores), and **the account is kept** (order history and payments keep pointing at it). To add the person again, invite the account. Role and membership writes share the company lock (`lockCompany`), so a role cannot be deleted while being given.

Sessions are read from the DB on every request (no cookie cache), so the switch applies at once and other sessions are untouched. **Tabs of one browser share the session:** the switcher announces the change on a `BroadcastChannel` and `CompanySwitchGuard` (dashboard layout) blocks any other tab still showing the old company until it reloads (Server Actions do not carry the company: worst case a write lands in the new active company, where the permissions are checked anyway).
- **Invitations for existing accounts (decided 2026-10):** "Add member" with an email that already has an account offers **"Create invitation link"** instead (`createInvitationAction` -> `createInvitation`, `src/server/invitations.ts`, `team:create`; rows in Better Auth's `invitation` table, written only by our code): role must be grantable, the account must exist (`noAccount`) and not be a member (`alreadyMember`), max 20 pending per company (`MAX_PENDING_INVITATIONS`, `src/lib/invitations.ts`), expires in 7 days; inviting the same email again refreshes the same invitation (same link). No email provider: the owner copies the link (`/<locale>/invite/<id>` on the panel host) and sends it by WhatsApp/Telegram. The Team page lists pending invitations (copy link, cancel). **The invite page** (`app/[locale]/invite/[id]`): signed out -> `/login?next=...` (the panel login now honors `?next=` through `safeNextPath`), temporary password -> change it first, impersonating -> 404; another account sees only which email it is for (+ "sign in with another account"); the invited account sees company, role, inviter, expiry and **Accept / Decline** (`respondToInvitationAction`). **Accepting re-checks everything under the company lock**: pending, not expired, the viewer's own email, not a member yet, the role still exists, and the inviter is still a member with `team:create` and every permission of the role; then the membership is created, the invitation marked `accepted`, and that company becomes the session's active one. The person keeps their own account and password.
- **The organization plugin only knows `owner`** (`auth.ts` builds its access control from the same statement). Its HTTP endpoints that create companies or change members/roles/invitations (`/organization/create`, `update`, `delete`, `*-invitation`, `invite-member`, `remove-member`, `update-member-role`, `leave`) are in `disabledPaths`: only our server code changes membership. In the admin list the company contact is its **oldest member** (not matched by role).

### Merchant signup (decided 2026-10)
- Merchants can register themselves (`/[locale]/signup`): the form creates the user (own password, no forced change), the company and the first store. **The store starts `pending`**: the merchant can log in and set up (products, branding) but the storefront is not public until the superadmin approves it in the admin panel (store `status`: pending | active | suspended, replacing `is_active`). The superadmin can still create merchants by hand.
- No email provider in the MVP: emails are not verified and recovery stays manual, so signup needs rate limiting (and a captcha/honeypot) before it is opened to the public.

- **Implemented:** `/[locale]/signup` (linked from the home and login pages) -> `signupAction` -> `registerMerchant()` (`src/server/signup.ts`): user with their own password (no forced change, email NOT verified), company with the user as owner, first store with status `pending`, and the user is signed in. Shares `findUnavailable` / `createCompanyAndStore` / `removeUser` (`src/server/provisioning.ts`) with the superadmin's `createMerchant`, which creates stores `active`.
- **Store status** (`store.status`, DB CHECK): `pending` (default) -> not public; `active` -> public; `suspended` -> not public again. The storefront only serves `active` stores (404 otherwise); the merchant panel keeps working in every status and shows a banner while the store is not active. The superadmin approves / suspends / reactivates in the admin list (pending stores are listed first); changes are not audited yet.
- **Abuse protection on signup** (no email verification yet): per-IP limits (`SIGNUP_MAX_ATTEMPTS`, default 10 per hour, and `SIGNUP_MAX_ACCOUNTS`, default 3 per day; in-memory sliding window in `src/server/rate-limit.ts`, resets on restart), a honeypot field and a minimum fill time of 1.5 s (client-reported, only a speed bump), plus the manual approval, which is the real gate.

### Customer accounts (decided 2026-10)
- **One global account, one `customer` record per company.** Signing up or logging in from a store's storefront creates the `customer` row (`tenant_id`, `user_id`) for that company if it does not exist. The planned `customers` table (guest checkout, by phone) gets a nullable `user_id`; guest orders can be linked to the account later.
- **Branded login/signup on the store's own subdomain** (`<slug>.qvashop.com/login`, `/signup`): reached from the QR code / store link, shows the merchant's logo and colors (from store branding, Phase 2), and returns to the same store after authenticating. The customer never leaves the store's domain.
- Session cookies stay **host-only** (no `crossSubDomainCookies`): a session on one store is not sent to another store or to `app.`/`admin.`. The same person signs in once per store with the same credentials.
- **Implemented (part 1, 2026-10):** pages `/login`, `/signup`, `/account` on the store subdomain (`stores/[slug]/{login,signup,account}`; branded through the store layout; `noindex`), the **store header** (`stores/[slug]/layout.tsx`): currency `Select` (shadcn, only with 2+ currencies), cart icon with the unit count on its corner (`cart-link.tsx`, hidden at 0), and the **account menu** (`account-menu.tsx`: shadcn `Avatar` with initials on the brand pair, or a person icon for guests, opening a `DropdownMenu` with My orders / My profile / theme / sign out, or sign in / create account / theme). Server Actions `src/server/customer-account-actions.ts` -> `src/server/customer-accounts.ts` (a public write like `checkout.ts`: `tenant_id` is read from the store row there). **The store is taken from the request's Host header** (`getStoreSlug`), never from the browser, so an account is only attached to the store it is used on. Sign-up/sign-in call `auth.api.signUpEmail` / `signInEmail` server side (the `nextCookies` plugin sets the host-only cookie) and then `ensureCustomer(storeId, user)`: the company's `customer` row for that account (`(tenant_id, user_id)` upsert that never overwrites an existing row; the account page calls it again, covering sessions started elsewhere). Defenses (server-side `auth.api` calls skip Better Auth's rate limiter): sign-up = per-IP limits (10 attempts/h, 5 accounts/day), honeypot and minimum fill time (shared with merchant signup); sign-in = 10 per 10 min per IP **and per email**; wrong password, unknown email and banned accounts all answer `invalidCredentials`. `?next=` (where to go afterwards) is sanitized by `safeNextPath` (a local path only; default `/account`). Sign-out ends this host's session only. A merchant or the superadmin can also sign in on a storefront as a customer (it is the same global `user` table; the panels stay on their own hosts).
- **Part 2 (2026-10): checkout and history.** `placeOrderAction` attaches the order to the account only when the session belongs to **this store's host** (the request's slug must be the Host's). Signed-in checkout: the form is prefilled from the account's `customer` record (still editable; the order keeps its own snapshot), `order.customer_id` = the account's record and `order.user_id` = the account. **The record takes the phone of its first order only if no other record of the company has that number**; otherwise nothing is merged (a typed phone proves nothing, so a guest record is never joined to an account). Guest checkout is unchanged (found by phone; a guest typing an account's phone is grouped under that record for the merchant, but gets no `user_id`). `/account` is the profile (name, email, sign out); **`/account/orders` lists only orders with `user_id` = the account on this store** (`listAccountOrders`, newest 50: number, local date, status, total, link to the confirmation page, which shows "See my orders" to its owner only). Guest orders never appear in a history, even with the same phone.
- **Favorites (decided 2026-10, migration `0026`): need a customer account.** A heart on every product card (top right, over the image; a **sibling** of the card's link, since a button inside an `<a>` is invalid) and next to the product page title (`favorite-button.tsx`). Table `favorite` (PK `(customer_id, product_id)`, `tenant_id`, `store_id`; composite FKs to `customer (id, tenant_id)` and `product (id, store_id, tenant_id)`, both `ON DELETE CASCADE`), so favorites belong to the company's customer record and a store's list only holds its own products. `src/server/favorites.ts` (public write: only active products of active stores can be added; max **200 per customer per store**, `MAX_FAVORITES` in `src/lib/favorites.ts`, counted under a lock on the customer row) <- `setFavoriteAction` (`favorite-actions.ts`: store from the Host via `getHostStore()` in `public-store.ts`, this host's session or `signedOut`, 60 per minute per account). The store layout loads the ids for the session and `<FavoritesProvider>` toggles them optimistically (reverts with an error toast). **A guest's click** opens a dialog (Sign in / Create account) linking to `/login?next=<this page>` (built from `window.location` without the locale prefix); the product waits in `sessionStorage` (`qvashop:pending-favorite`, forgotten after 30 min) and the provider saves it with a toast once the shopper is back signed in. `/account/favorites` (in the account menu) lists them newest first in the shopper's currency (`listPublicProductsByIds`); products no longer public or not sold in that currency are left out.

### Orders (schema done 2026-10, migration `0011`; checkout, merchant list/detail, status changes and manual payments built)
Orders are created at storefront checkout (guest checkout, no customer account). Merchants manage them in the panel. Tables in `app-schema.ts` (singular names like the rest; `order` is a reserved word, so raw SQL must quote it: `"order"`):

| Table | Purpose / key fields |
|---|---|
| `customer` | Per **company** (`tenant_id`, shared by its stores). `name`, `phone` (normalized by the app, see Phone numbers: international `+<digits>` when the country is known, DB format check, **unique per company** when set), `email`, `user_id` (nullable, for customer accounts later; unique per company). Guest checkout finds/creates it by phone. |
| `order` | `tenant_id`, `store_id`, `number` (unique per store, from `store.last_order_number`), `customer_id` (nullable, `SET NULL ("customer_id")`), `user_id` (the customer account that placed it while signed in, `SET NULL`; null = guest; migration `0014`), **snapshot** `customer_name` / `customer_phone` / `customer_email`, `customer_note`, `status`, `payment_status`, `fulfillment_type`, `currency_code` (FK to the platform `currency`, not `store_currency`, so removing a currency never touches old orders), `subtotal_minor`, `delivery_fee_minor`, `total_minor` (bigint; DB check `total = subtotal + delivery_fee`), `idempotency_key` (unique per store), timestamps. |
| `order_item` | Composite FK to `order (id, store_id, tenant_id)`; `variant_id` / `product_id` link back to the catalog with `SET NULL (<column>)` when deleted; **snapshot** of product name, variant title, SKU, unit price (after tiers/promotions), compare-at, quantity, line total (DB check `line_total = unit_price * quantity`), `stock_deducted`, `position`. Never read the live product or price for an existing order. |
| `order_status_history` | `from_status` (null = order placed), `to_status`, `actor` (`customer` \| `merchant` \| `system`), `actor_user_id` (SET NULL), note, timestamp. Written in the same transaction as every status change. |
| `order_payment` | Manual records: `kind` (`payment` \| `refund`), `method` (`cash` \| `transfer` \| `other`), `amount_minor` (> 0, always in the order's currency), `paid_at`, `recorded_by_user_id`, note. No gateway involved. |
| `order_delivery` | Migration `0017`. 1:1 with delivery orders (PK `order_id`, composite FK to the order): snapshot of the typed `address`, the customer's pin (`location_lat`/`location_lng`), `distance_m` (straight line from the store) and the store's `fee_mode` at that moment. The fee itself is `order.delivery_fee_minor`. Time slot: later. |

- **Order number:** checkout runs `UPDATE store SET last_order_number = last_order_number + 1 ... RETURNING` inside the order's transaction (the row lock serializes concurrent checkouts; a rollback leaves no gap). Format it for display in the app (e.g. `#1001` is a display choice, the column starts at 1).
- **Customer snapshot:** reusing a customer by phone must not overwrite another order's data; the order keeps what was typed at checkout. Do not show a customer's other orders to someone who only typed their phone.
- **Stock:** checkout takes the stock in the same transaction (`UPDATE product_variant SET stock = stock - qty WHERE ... AND stock >= qty`; the `stock >= 0` check is the last guard) and sets `order_item.stock_deducted` when the variant tracked stock. Cancelling gives stock back only for lines with `stock_deducted` whose variant still exists and still tracks stock, then clears the flag on every line (so it can never happen twice; `cancelled` is final too).
- **Idempotency:** the checkout form sends a random key per attempt; a retried submit finds the existing order (`order_store_idempotency_key_unique`) instead of creating a second one.
- Hand edit in `0011`: the three `SET NULL` FKs use a column list (same reason as `0008`).
- **Order status:** `pending → confirmed → preparing → ready → out_for_delivery → completed`, plus `cancelled` from any non-final state. `out_for_delivery` only applies to `delivery` orders (DB check).
- **Payment status:** `unpaid | partial | paid | refunded` — a cache of `order_payment` (net = payments − refunds; `refunded` when there are refunds and net ≤ 0), recomputed by the app in the same transaction that adds/removes a payment, never edited directly.
- **Merchant panel:** `/dashboard/orders` (permission `order:read`, all three roles; "Pedidos" is the second sidebar item) is a **server-driven data table** (`orders-table.tsx`: TanStack Table with `manualSorting` / `manualFiltering` / `manualPagination`; toolbar, faceted filters, column visibility and pagination as in the shadcn data-table docs, shared pieces in `src/components/data-table/`). The table only holds the current page: **every state change becomes a new URL** (`?status=pending,ready&payment=unpaid&q=&from=&to=&tz=&sort=-total&page=2&size=20`), parsed and serialized by `parseOrderListParams` / `orderListQuery` (`src/lib/order-list.ts`; bad values are ignored, defaults left out), and the server filters, sorts and pages in SQL. Search (`q`: `12` / `#12` = order number, otherwise part of the name, or 3+ digits of the phone) follows the typing (debounced 400 ms, `router.replace`) and is also a GET form for Enter before hydration. Status and payment are multi-select faceted filters whose counts (`countOrderFacets`) follow every other filter but their own. Sort: date (default newest first), customer (ICU collation, accents ignored), total (grouped by currency first); always one sort, no "unsorted". Page sizes 20 / 50 / 100 (default 50). Row `...` menu: view order, call, WhatsApp (numbers with `+` only). **Date filter** (`date-filter.tsx`, a popover in the toolbar): presets Today / Yesterday / Last 7 days / This month (computed in the browser's zone) and a range calendar; a link carrying another timezone says which zone its days are in. `/dashboard/orders/[id]`: items (snapshot, SKU, struck-through compare-at, "product deleted" note), totals, customer with `tel:` / WhatsApp (`wa.me`, only for numbers with `+`) / `mailto:` links and note, payments, history (who and when). Queries in `src/server/orders.ts` (tenant + store scoped; another company's order is a 404); client-safe enums and badge styles in `src/lib/orders.ts` (`satisfies` the schema lists). Dates use `<LocalDateTime>` (browser timezone).
- **Status changes** (`order:update`, all three roles; `status-actions.tsx` on the order page -> `changeOrderStatusAction` in `src/server/order-actions.ts` -> `changeOrderStatus` in `src/server/orders.ts`): the next step in one click, later steps in an "Other status" menu (**steps may be skipped**, e.g. a pickup completed on the spot), and cancel. **Never backwards**; `completed` and `cancelled` are final, so those two ask for confirmation and take an optional note (max 500, kept in the history, team only). The allowed moves live in one pure function, `nextStatuses(status, fulfillmentType)` / `canChangeStatus` (`src/lib/orders.ts`), used by the buttons and re-checked on the server. One transaction: lock the order row, refuse with `stale` if its status is no longer the `from` the page showed (another team member moved it; the page refreshes), update the status, restock on cancel, write the history row (actor `merchant`, `actor_user_id` = the signed-in user; while impersonating that is the merchant, see `impersonation_log`). Checkout and cancel both lock variants **in id order**, so they cannot deadlock. Cancelling a paid order does not refund anything by itself: the merchant records the refund.
- **Manual payments** (`order:update`; `payments-section.tsx` on the order page -> `recordPaymentAction` / `deletePaymentAction` in `src/server/order-actions.ts` -> `src/server/order-payments.ts`): the section shows collected (net), refunded and due, and the records (kind, method, date, who, note). Recording: kind payment | refund, amount in the **order's currency** (decimal string -> minor units with `parsePriceToMinor(..., Number.MAX_SAFE_INTEGER)`, since an order can exceed the product price cap), method cash | transfer | other, optional date (`datetime-local` in the browser's zone -> ISO; empty = now; not in the future) and note. **Limits keep the balance between 0 and the total:** a payment at most what is due, a refund at most what was collected; a cancelled order takes refunds only. Removing a record (to fix a mistake) is refused (`unbalanced`) if it would break the same rule. Each write locks the order row, re-checks the limits against the stored records and **recomputes `payment_status` in the same transaction** (`paymentStatusOf` / `paymentTotals` in `src/lib/orders.ts`, pure). Not audited yet: a removed record is gone (only `recorded_by_user_id` / `created_at` exist on live rows).
- **Money:** integer minor units (e.g. cents) + currency code, `bigint` columns (currencies like CUP reach large amounts). Never floats.
- Order totals are computed server-side at checkout; the client never sends prices.

### Home delivery (Phase 5, decided 2026-10)
- **Where:** the merchant places the store on a map (orders leave from there) and **draws the service area as a polygon** (click corner by corner; undo last point, clear). Not a list of neighborhoods, not a radius. At checkout the customer drops a pin; the order is accepted only inside the polygon (point-in-polygon, checked on the server).
- **Distance = straight line** (haversine) between the store pin and the customer pin, computed on our server; no routing engine.
- **Fees (step 2, built 2026-10, migration `0016`):** on `store_delivery`: `delivery_enabled` (default off), `pickup_enabled` (default on; DB check: at least one is on), `fee_mode` free | flat | distance, `base_distance_m`; DB check: delivery on needs a location and an area. Table **`store_delivery_rate`** (per store currency, PK `(store_id, currency_code)`, FK to `store_currency` `ON DELETE CASCADE`, so removing a currency removes its amounts): `base_fee_minor` (flat: the fee; distance: covers the base distance), `per_km_minor`, `free_above_minor` (null = never), `min_order_minor` (null = none). **Rules in `deliveryFee()`** (`src/lib/delivery.ts`, pure, unit tested): below the minimum = refused; free mode or subtotal >= free-above = 0; flat = base fee; distance = base fee + per-km x **each started km** beyond the base distance (1 m over = 1 km). A currency without a row has no delivery in flat/distance mode (`noRate`); the default currency's fee is required by the form. Same file: `distanceMeters()` (haversine) and `insideArea()` (ray casting) for checkout. Form: `delivery-charges-form.tsx` (switches, mode select, km with up to 3 decimals, one card per currency; empty or 0 = never / no minimum) -> `saveDeliveryChargesAction` -> `saveDeliveryCharges` (replaces the rates). The map area cannot be cleared while delivery is on (`deliveryNeedsArea`). Time slots come later; until then the customer can write a preferred time in the note.
- **Gotcha:** an upsert (`INSERT ... ON CONFLICT DO UPDATE`) checks CHECK constraints on the proposed new row first, so `store_delivery` with `delivery_enabled = true` is **updated** in place, never upserted.
- **Built (step 1):** table `store_delivery` (1:1 with store, migration `0015`: `location_lat`/`location_lng` double precision, `service_area` jsonb of `[lng, lat]` corners, GeoJSON order, not closed, 3 to 200 corners by DB check; composite FK to the store). Settings > **Delivery** (`/dashboard/settings/delivery`, `store:update`): `delivery-area-form.tsx` (map modes "place the store" / "draw the area", draggable store marker) -> `saveDeliveryAreaAction` (`catalog-actions.ts`) -> `saveDeliveryArea` (`src/server/delivery-settings.ts`), schema `createDeliveryAreaSchema` (`lib/validation/delivery.ts`).
- **Checkout (step 3, built 2026-10):** the storefront reads the settings through `getPublicDelivery(storeId)` (`src/server/public-delivery.ts`, public read: pickup on/off and, when delivery is on and the map is set, mode, base distance, store pin, area, amounts per currency). The form offers pickup / delivery (delivery greyed out "not available paying in X" when the currency has no amounts and the mode is not free); delivery shows `<DeliveryPinMap>` (area drawn, store marker, a draggable customer pin set by tap, drag or "use my location" (browser geolocation)) and a required address textarea (street, number, references). The order stores `fulfillment_type = delivery`, `delivery_fee_minor`, `total = subtotal + fee` and the `order_delivery` snapshot; the confirmation page shows the address and the fee.
- **Merchant order view (built 2026-10):** `getOrder` returns the `order_delivery` snapshot; the order page shows a "Home delivery" card (typed address, straight-line distance, fee or "Free" and the fee mode used, a read-only map with the pin (`order-location-map.tsx`), links to open the pin in Google Maps / OpenStreetMap for the courier, and the coordinates as text); the totals show the fee row for every delivery order. The list marks delivery orders with a truck icon. Only plain links leave our site: the pin goes to Google/OSM only if the merchant clicks.

### Exchange rates (decided 2026-10, migration `0028`)
- Why: in Cuba's informal market USD/EUR/CUP rates move often (1 USD = 750, 800, 860 CUP...). Rewriting every price on each change is error-prone (merchants forget products), so **rates are stored, not prices**.
- `store_currency`: `is_base` (exactly one per store, unique partial index; migration backfilled it from `is_default`; new stores: their first currency), `exchange_rate` numeric(20,8) = units of this currency per 1 base unit (null = no automatic prices; the base has none, DB CHECK), `rounding_minor` (automatic prices are a multiple of it, null = 1; must be one of `roundingSteps(digits)`: 1, 5, 10, 50... up to 100 major units). **Base** = the currency prices are typed in; **default** = what shoppers see first (independent).
- A variant's prices in a currency are, **per group** (regular prices with their tiers, and each promotion): its own rows there (**manual**) or, if none and the currency has a rate, its base rows converted (**auto**, nothing stored). `pricesIn()` / `convertMinor()` in `src/lib/exchange.ts` (pure, BigInt, round half up to the step, a positive price never rounds to 0, a converted "was" price not above the price is dropped). Changing a rate changes every automatic price at once; orders keep their snapshot.
- Server: `loadPriceRows` (storefront, cart, checkout) and `loadRegularPrices` (merchant: products table, promotions) in `src/server/pricing.ts` read the target and base rows and derive; store currencies are read once per request (`storeCurrencies`, React `cache`).
- Settings > Currencies (`currencies-form.tsx`, react-hook-form): base select (changing it re-expresses the rates per the new base with `rebaseRates`, editable before saving), per currency "1 USD = [rate] CUP" and rounding, default radio. **Changing the base is refused** (`baseMissingPrices`, with the count) while some product has a regular price in the old base but none in the new one; the old base's rows then simply become manual prices.
- Products table: a currency switch (ButtonGroup, 2+ currencies) shows the price in that currency with an Auto / Manual / Mixed badge (`listProductPrices`); with `product:update`, rows can be selected (TanStack `rowSelectionFeature`) for **bulk actions** (`src/server/bulk-prices.ts`, one SQL statement each, regular rows only, promotions untouched): **Follow the rate** (deletes the manual rows in that currency; refused for the base and for a currency without a rate) and **Adjust %** (`parsePercent`: -90..1000 %, 2 decimals; scales price, tiers and "was" price, rounded to the currency's step; products following the rate are skipped; refused as a whole with `tooHigh` past `MAX_PRICE_MINOR`).
- Delivery fees stay per currency (no conversion).

### Maps (decided 2026-10)
- **Base map = one PMTiles archive** (Protomaps vector tiles cut from the OpenStreetMap-based daily build, bbox of Cuba `-85.1,19.7,-74.0,23.4`, `MAP_BOUNDS` in `src/lib/map.ts`) stored in our bucket at `platform/maps/cuba.pmtiles` (`MAP_ARCHIVE_KEY`). The browser asks **`/api/map/tiles/{z}/{x}/{y}`** (same origin on every host, store subdomains included); the route reads that tile from the archive with an S3 range request (`src/server/map-tiles.ts`, `pmtiles` library, header/directories cached per process; a failed read drops that cache so the next request retries) and returns it **uncompressed** (pmtiles already decompresses tiles, and Next undoes a gzip set by a route handler), cached a day; compression is the edge's job (pre-launch checklist). 204 = no tile there (outside the archive), 503 = archive unreadable (`<BaseMap>` then shows one notice instead of an error per tile). Why: CARTO basemaps need a paid license for commercial use and the public OSM tile servers may block commercial apps at any time; this way there is no key, no per-view fee and no third party.
- **Style:** `@protomaps/basemaps` `layers("protomaps", namedFlavor("light"), { lang })`. Fonts (Noto Sans Regular/Medium/Italic, Latin ranges 0-255, 256-511, 8192-8447) and the "light" sprites are static files in `public/map/`, copied from `protomaps/basemaps-assets` (commit `028c18f`; Noto fonts are OFL). Attribution "© OpenStreetMap" must stay visible.
- **MapLibre's worker:** v6 loads its Web Worker by URL next to its own file, which does not exist once bundled, so `scripts/copy-map-worker.mjs` copies `maplibre-gl-worker.mjs` + `maplibre-gl-shared.mjs` to `public/map/vendor/<version>/` before `dev` and `build` (package.json scripts; the folder is gitignored) and `<BaseMap>` calls `setWorkerUrl`. `<BaseMap>` (`src/components/map/base-map.tsx`) is the only place that creates a map; maplibre is imported dynamically, so only map pages load it.
- **The map cannot be edited in the app.** Missing streets, buildings or house numbers are fixed in OpenStreetMap itself (openstreetmap.org editor) and show up after the next refresh of the archive. Store-specific points drawn on top would be a separate feature (Parking Lot). Checkout must never depend on the map being complete: the customer's pin plus a typed address/reference is enough.
- **Refreshing the archive** (e.g. every few months), from the repo root:
  1. Pick a build from `https://build-metadata.protomaps.dev/builds.json` (key `YYYYMMDD.pmtiles`).
  2. `docker run --rm -v "<dir>:/data" protomaps/go-pmtiles:v1.31.2 extract https://build.protomaps.com/YYYYMMDD.pmtiles /data/cuba.pmtiles --bbox=-85.1,19.7,-74.0,23.4`
     - On a machine whose antivirus inspects HTTPS (Avast here) the container rejects the certificate: mount a CA bundle that includes the antivirus root, `-v "<bundle>:/etc/ssl/certs/ca-certificates.crt:ro"` (export the root from the Windows certificate store). Never disable TLS verification.
     - On a slow or unstable connection add `--overfetch=0 --download-threads=8` (many small requests instead of a few large ones; long downloads were cut with "unexpected EOF"). `--dry-run` shows the size first: all of Cuba is about 136 MB.
  3. `cd apps/web && node --env-file=../../.env scripts/upload-map.mjs <dir>/cuba.pmtiles` (the tile route picks it up on the next failed or fresh read; restart the app to be sure).
- **Local development uses a Havana-only archive** (bbox `-82.55,22.95,-82.1,23.2`, about 12 MB) uploaded under the same key: the full Cuba download was too slow here. Outside Havana the dev map shows only the background. Build the full archive on the VPS (fast connection).

### Product images (decided 2026-10)
- **Hard limit: each stored image is under 1 MB** (`MAX_IMAGE_BYTES = 1_000_000`), max **6 images per product**, JPEG/PNG/WebP only. Constants and the type/size checks live in `src/lib/images.ts`.
- **Browser** (`src/lib/compress-image.ts`, `browser-image-compression`): resizes to at most 1600 px on the long side and re-encodes to WebP targeting 0.9 MiB (**JPEG instead where the browser cannot encode WebP**, notably Safari, which silently returns PNG; detected at runtime with `canEncodeWebp()`); originals up to 20 MB are accepted for compression. Re-encoding through a canvas also strips EXIF (GPS, camera). `useWebWorker: false` on purpose: the library's default worker is downloaded from cdn.jsdelivr.net at runtime, and we do not run third-party code on merchants' pages.
- **Server** (`src/server/product-image-actions.ts` -> `product-images.ts`) never trusts the client: it re-checks size (> 1 MB is refused), detects the real type from the file's magic bytes (the browser-reported type and file name are ignored; SVG/HTML are refused), requires `product:create` or `product:update`, and derives the key extension from the detected type. Uploads are Server Actions with `experimental.serverActions.bodySizeLimit: "2mb"` in `next.config.ts` (the default is 1 MB and multipart adds overhead).
- **Saved with the product form (decided 2026-10, migration `0027`):** images are a field of the product form (`product-images-field.tsx`, on `/new` and `/[id]/edit`), not a separate step. Files are picked with **`<Dropzone>`** (`src/components/ui/dropzone.tsx`, our own, no library: a `<label>` around a hidden file input, so drag-and-drop plus click/keyboard; `accept` filter with `onFiles` / `onReject`; text comes from the caller through `DropzoneTitle` / `DropzoneDescription`). Every image upload uses it (products, logo / logotype, main and secondary banners); no plain file inputs. **Picking a file stages it**: `stageProductImageAction` uploads the file and records a `product_upload` row (tenant, store, uploader; no product yet), max 30 unsaved per store (`MAX_PENDING_UPLOADS`, counted under a store-row lock). The form value `images` is the ordered list of refs (`{ kind: "existing" | "upload", id }`, first = main); remove / make main only change that list, and Save is disabled while uploads are in flight. **Save applies it in the product's transaction** (`applyProductImages`): staged rows move to `product_image` (same storage key, the file never moves), images left out are deleted, positions follow the list; an unknown id answers `imagesStale` and rolls the whole save back. Files of removed images are deleted after the commit. Leaving without saving changes nothing; staged uploads older than a day are swept (rows, then files) on the store's next upload, and removing a fresh upload from the form discards it right away. `deleteProduct` removes all its files. Keys: `tenants/<tenantId>/products/<uuid>.<ext>` (older images: `products/<productId>/<uuid>.<ext>`, still valid).
- **Deleting a whole company must also delete its `tenants/<tenantId>/` prefix in storage** (a database cascade only removes rows). Not implemented yet because there is no delete-company feature.
- Images are shown with a plain `<img>` pointing at the public bucket URL (`publicUrl(key)`); `next/image` is not used (it would need `sharp` and a remote host config for the bucket).

### Public storefront (Phase 3)
- Internal routes under `/[locale]/stores/[slug]/` (reached through the subdomain rewrite in `proxy.ts`): `layout.tsx` (resolves the store, 404 unless `active`, sets the brand CSS variables, header), `page.tsx` (catalog) and `products/[id]/page.tsx` (product page: gallery, price, description, stock hint). Public URLs: `<slug>.qvashop.com/es` and `<slug>.qvashop.com/es/products/<product-slug>` (an id in that segment redirects to the slug).
- **Public reads** live in `src/server/public-store.ts` (store by slug) and `src/server/public-catalog.ts` (products). They run without a signed-in tenant, so safety is in the query: a product is joined to its store by the composite key (`store_id`, `tenant_id`), and only `active` products of `active` stores are returned (draft, archived, pending and suspended do not exist for the public). `tenant_id` never leaves these files. Add any new public read there, with the same rules.
- Visitors see: `stock = 0` -> "Agotado" badge; `stock` 1 to 5 -> "Quedan solo N"; untracked stock (null) -> nothing. Descriptions are plain text (React escapes it, line breaks kept): never render merchant text as HTML.
- Storefront pages use the brand only through CSS variables (`var(--brand)`, `--brand-accent`, and their `-foreground` pairs); the price stays neutral so a light brand color never hurts readability.
- **Product search (decided 2026-10):** `/search?q=` on the store subdomain (`stores/[slug]/search/page.tsx`, `noindex`, max 60 results). `searchPublicCatalog` (`public-catalog.ts`) matches in the app with `searchScore` (`src/lib/search.ts`: every word must appear; case and accents ignored, so `cafe` finds `Café`; name > tags/visible category > description). Fine for MVP catalog sizes; move to SQL (`unaccent` / full-text) if catalogs grow. **Suggestions while typing** (`search-autocomplete.tsx`): `GET /api/store-search?q=` (`src/app/api/store-search/route.ts`; `/api` is outside the proxy, so the store is the request's Host via `getStoreSlug`, never a parameter; shopper's currency cookie; from 2 characters, top 6 (`SUGGEST_*` in `lib/search.ts`), only those get priced; 120 per minute per IP; `Cache-Control: private, max-age=30` + `Vary: Cookie`). Enter on a highlighted suggestion opens it (items render as `Link`; Base UI clicks the highlighted item), Enter otherwise goes to the results page; the last option is "See all results". A GET route, not a Server Action: actions run one at a time per client and cannot be aborted. The field (`store-search.tsx`, a GET form like the orders search, remounted per page/query through its `key`) sits **inside the main bar from `md` up**, and on phones in **a second row under it, same brand background, that slides away while scrolling down and comes back on any scroll up**; the main bar (logo, cart, account) never moves. Not shown on `/checkout`. The layout exposes `--store-sticky` (what is pinned at the top right now, via `:has([data-search-hidden])`): anything sticky below the header uses it (the category index does). The hide-on-scroll logic lives in `use-hide-on-scroll.ts` (`useHideOnScroll(ref)`), shared by every bar under the header.

### Cart (Phase 3)
- **The cart lives in the browser** (localStorage key `qvashop:cart:v2:<storeId>`; each store subdomain is its own origin, so carts are separate) and holds **only `{ variantId, quantity }`** (`src/lib/cart.ts`). Names, prices and stock are never stored: a tampered cart cannot change a price. `parseCart` drops anything invalid (bad ids, quantities out of 1..99, extra fields such as a price), merges duplicates and caps the cart at 50 lines.
- **The server is the only source of amounts:** `priceCartAction(slug, currency, items)` -> `priceCart(storeId, currencyCode, items)` (`src/server/cart.ts`) re-reads each variant, resolves its unit price for the quantity (volume tiers, active sales) with the public rules (active product in an active store), applies the stock (`null` = up to 99) and returns per-line `status`: `ok`, `reduced` (asked for more than the stock; quantity lowered), `soldOut`, `unavailable` (hidden, deleted, another store's, or no price in the chosen currency: no name is revealed for the first three), plus the subtotal. Invalid entries are skipped one by one, never failing the whole cart. Rate limited per IP (120 per minute). **Checkout must call `priceCart` again and never trust any amount from the browser.**
- Cart page (`/cart` on the store subdomain): shows what the customer has with the prices the server sent, updates instantly on +/-/remove and re-prices right after; a quantity the server lowered keeps an explanation ("Solo quedan N") until the customer touches that line. Product pages offer a quantity picker limited to the free stock (stock minus what is already in the cart); sold-out products have no add button. The header shows the unit count and follows other tabs (`storage` event).
- Known quirk: the header counter comes from storage, so it also counts lines that turn out to be unavailable until the customer opens the cart and removes them.
- Money: a cart can reach 50 lines x 99 units x 10 000 000 major units, so **order totals must be stored as bigint**, not PostgreSQL `integer`.

### Checkout (Phase 3, done 2026-10; home delivery added in Phase 5, see Home delivery)
- Pages on the store subdomain: `/checkout` (`stores/[slug]/checkout/`: contact form + pickup info from Settings > Pickup + summary priced by `priceCartAction`) and `/orders/<id>` (confirmation: number, items, total, pickup and store contact; `noindex`; the random order id in the URL is the key and the order must belong to that store; it shows no status, a tracking page is in the Parking Lot). The cart page links to checkout when at least one line can be bought; lines that are sold out or unavailable are simply left out of the order (the summary says how many).
- **`placeOrderAction`** (`src/server/checkout-actions.ts`) -> **`placeOrder`** (`src/server/checkout.ts`, the public write: like `public-*.ts`, `tenant_id` is read from the store row there and never leaves the file). The browser sends the slug, the currency it showed, the items (`sanitizeCartItems`, shared with `parseCart`), the subtotal it showed (only compared, never used as an amount), a random **idempotency key** per checkout attempt, and the contact form (`createCheckoutSchema`; phone normalized with `normalizePhone(phone, country)` in `src/lib/phone.ts`, see Phone numbers below). Any difference (price, stock, line, currency) answers `cartChanged` and the form re-prices so the customer confirms the new amounts.
- **One transaction:** lock the store row (`FOR NO KEY UPDATE`, serializes a store's checkouts) -> same idempotency key already used = return that order -> `last_order_number + 1` (store `updated_at` kept) -> lock the variants and subtract stock where tracked (refuse if short) -> upsert the customer by `(tenant_id, phone)` without overwriting it -> insert order, items (snapshot, `stock_deducted`) and the first history row (`null -> pending`, actor `customer`). Any refusal throws inside the transaction, so nothing is kept, not even the number.
- **Abuse:** each order takes stock, so fake orders could empty a store. `placeOrderAction` is limited to 10 per 10 minutes per IP (in memory, see `rate-limit.ts`); retries count too. The merchant cancelling an order (Phase 4) must give stock back for lines with `stock_deducted`.

### Phone numbers (decided 2026-10)
- **Store setting** `store.phone_country` (ISO 3166-1 alpha-2, migration `0013`; null = none), chosen in Settings > General. It is **preselected at checkout**; the customer can change it.
- **Supported countries** live in `src/lib/countries.ts` (`PHONE_COUNTRIES`: code, calling code, national trunk prefix; no library). Now: Cuba, US, Spain, France and Italy. Names come from `Intl.DisplayNames` in the page locale and are **computed on the server** (`phoneCountryOptions(locale)`) and passed to client components, so server and browser render the same text. Adding a country = one entry (check its trunk prefix: Italy has none, its 0 is part of the number).
- **`normalizePhone(input, country)`** (`src/lib/phone.ts`): `+` or `00` = international as typed; otherwise the country's code is added and its trunk prefix dropped (`5 435 3930` + Cuba = `+5354353930`, `06 12 34 56 78` + France = `+33612345678`); without a country, just the digits. So the same person is found again however they type it, and WhatsApp links work (`wa.me` needs the country code).
- **UI**: `<CountrySelect>` (`src/components/country-select.tsx`, shadcn **Select** on Base UI: "Cuba +53" options, `compact` trigger "CU +53") and `<PhoneInput>` (country select + tel input). No flags for now (planned later; add them in `CountrySelect` only).
- `phoneCountrySchema` refines with an explicit `: boolean` return: TypeScript would otherwise infer a type predicate from `isPhoneCountryCode` and narrow the form's field type to the codes.
- Phones saved before this setting existed stay as typed (e.g. `54353930`); there is no automatic rewrite.

### Store banner (decided 2026-10, migrations `0018`, `0019`, `0020`)
- A **hero carousel** at the top of the storefront home page. Banners are images only, and merchants put their text inside the image, so an image must never be cropped to a shape it was not made for. Hence **two independent lists per store, by `device`**: `desktop` images are shown only from the `md` breakpoint (48rem = 768 px) up, `mobile` images only below it. - Table `store_banner_image` (like `product_image`: `storage_key`, `content_type`, `size_bytes`, `device` (DB CHECK, `BANNER_DEVICES`), `position` counted per device; composite FK to the store `ON DELETE CASCADE`). - Settings > Banner (`/dashboard/settings/banner`) uses the **shadcn Tabs** component (`components/ui/tabs.tsx`, Base UI; `variant="line"`) in `banner-tabs.tsx`: "Banner principal" | "Banner secundario". Server: `src/server/store-banner.ts` (writes lock the store row, so the limit and positions hold under concurrent saves) + `banner-actions.ts` (the upload's `device` is validated with `z.enum`). The shadcn `carousel.tsx` was adapted: no hard-coded English labels (pass `aria-label`) and the Embla state is read with `useSyncExternalStore` (the generated setState-in-effect failed lint).
- **Secondary banner** (migration `0020`): an optional row **under the hero**, used for promotions. It is the same fade + autoplay carousel, but **each slide is a pair of tiles side by side** that change together, and it has **no controls**. One complete pair = static.
  - Table `store_secondary_banner_pair`: one row per slide (`device`, `position`, and `left_*` / `right_*` storage key, type and size; each side is all-set or all-null by CHECK). Max 5 pairs per device. Files under `tenants/<id>/stores/<id>/banner/secondary/`.
  - **A pair missing a side is never shown**: `listPublicSecondaryBanner` returns complete pairs only, and settings mark the pair "Incompleta".
  - Tile formats (`SECONDARY_BANNER_FORMATS`): desktop 960 × 260 (the hero's panoramic shape at half width), mobile 600 × 600 square (a tile is about 170 px wide on a phone, so a flatter tile would make its text unreadable).
  - **Locked until the main banner has images:** the tab is `disabled` (its panel is not rendered, and `?tab=secondary` falls back to the main tab), and `createSecondaryPair` refuses `needsHero`. On the storefront, a device shows it only if the hero has images for that device.
  - **On/off switch** `store.secondary_banner_visible` (default on): hides it without deleting the images.
  - Server: `src/server/secondary-banner.ts` (create an empty pair, set or replace one side, move, delete the pair and both files, switch; every write locks the store row) + `secondary-banner-actions.ts`.

### Store footer (decided 2026-10, migrations `0022`, `0023`, `0024`)
- **Brand column, always shown:** the logotype alone when there is one (same rule as the header), otherwise logo + name, linking home; below it the merchant's **short text** (`store.footer_text`, plain text, max 300 (`FOOTER_TEXT_MAX`), line breaks kept, null = none). Then the link groups.
- **Link groups** (e.g. "Accesos": Preguntas frecuentes, Contacto) stored as **jsonb on the store** (`store.footer_links`: `[{ title, links: [{ label, url, newTab }] }]`, null = none; DB CHECK: an array). Not tables: the list is small, optional, always read and written whole, and never queried by link. **Array order is the display order** (no index field).
- Limits and rules in `src/lib/footer.ts`: max 4 groups x 8 links, a group needs at least one link. **`isSafeLinkUrl`**: only `http(s)://` with a host, `mailto:`, `tel:` or a store path (`/...`, not `//`); `javascript:`, `data:` etc. are refused, since the URL lands in an href on every storefront page. Checked on write (`createFooterLinksSchema`) **and on read** (`parseFooterLinks` drops anything malformed), because the DB only checks the array type. `normalizeLinkUrl` turns "tienda.com" into "https://tienda.com" on blur.
- Settings > **Footer** (`/dashboard/settings/footer`, `store:update`): shadcn Tabs (`footer-tabs.tsx`, open tab kept in `?tab=links` like the banner tabs; the list lives in `footer/tabs.ts` because a `"use client"` module cannot hand plain values to the server page): "Sobre la tienda" first (`footer-text-form.tsx`: one textarea with a counter -> `updateFooterTextAction`), "Enlaces" (`footer-links-form.tsx`: nested `useFieldArray`, groups -> links, move up/down, new-tab switch) and "Redes sociales" (`footer-social-form.tsx`, see below). `updateFooterLinksAction` / `updateFooterSocialAction` (`catalog-actions.ts`) return field errors keyed by their full path (`groups.0.links.2.url`).
- **Social media** (migration `0024`): `store.footer_social` jsonb `[{ network, url }]` (array order = display order, **one entry per network**, null = none; DB CHECK: an array). Networks in `SOCIAL_NETWORKS` (`src/lib/social.ts`): Facebook, Instagram, WhatsApp, Telegram, TikTok, X, YouTube, each with its **allowed domains**: `isSocialUrl` requires `https://` + a safe link + the network's domain or a subdomain of it (so a Facebook icon can never point elsewhere); checked on write (`createFooterSocialSchema`, which also rejects a repeated network) and on read (`parseFooterSocial`). Shown as outlined icons under the short text, **always opening in a new tab** (`aria-label` "Instagram (opens in a new tab)").
- **Icons:** Tabler Icons **outline** (MIT, v3.48.0, `https://tabler.io/icons`, files `icons/outline/brand-<name>.svg` of the `@tabler/icons` package) copied to `apps/web/public/icons/social/<network>.svg` with their `LICENSE`. `<SocialIcon>` (`src/components/social-icon.tsx`) draws them as a **CSS mask filled with `currentColor`** (an `<img>` SVG cannot take the text color), so they follow the theme and hover colors. Adding a network = its SVG there + an entry in `SOCIAL_NETWORKS` (+ its domains).
- Storefront: `stores/[slug]/store-footer.tsx` in the store layout (every page); plain `<a>` (a store path gets its locale from the proxy), `target="_blank" rel="noopener noreferrer"` for new-tab links.

### Custom pages (decided 2026-10, migration `0025`)
- Merchants create their own pages ("Sobre nosotros", "Envíos", FAQ...) served at the **root of the store**: `<slug>.qvashop.com/<locale>/<page-slug>` (route `stores/[slug]/[pageSlug]/page.tsx`; the storefront's static routes win over the dynamic segment).
- Table `store_page` (`title`, `slug` unique per store, `content` plain text, `status` draft | published, `meta_title`, `meta_description`; composite FK to the store `ON DELETE CASCADE`). Drafts are a 404 for the public; only published pages are read (`getPublicStorePage` in `public-store.ts`).
- **Limits** (`src/lib/store-pages.ts`): max **20 pages per store** (checked under a store-row lock), title 80, content 20 000 characters, meta 70/160. **Reserved slugs** (`RESERVED_PAGE_SLUGS`): the storefront routes (`products`, `cart`, `checkout`, `orders`, `login`, `signup`, `account`) plus names kept for the platform (`api`, `admin`, `search`, `pages`, `track`...). **A new storefront route must be added to that list** (an existing page with that slug would otherwise be shadowed).
- **Content is never HTML.** It is plain text with a few marks (`#` / `##` / `###` headings = h2 / h3 / h4 since the page title is the h1, a line of `---` / `***` / `___` = divider, `-` / `1.` lists, `**bold**`, `[text](url)` and bare `https://` links, blank line = new paragraph), parsed by `parsePageContent` into blocks and rendered as React elements by `<PageContent>` (`src/components/page-content.tsx`). Links must pass `isSafeLinkUrl` (same rule as the footer), otherwise they stay as text; external links open in a new tab. No images in pages yet.
- Settings > **Pages** (`/dashboard/settings/pages`, `/new`, `/[id]`; `store:update`): list (status, public link), form (title, slug filled from the title on new pages and editable, content with Write / Preview tabs and a format help, published switch, SEO), delete with confirmation. Server: `src/server/store-pages.ts` + `store-page-actions.ts`. Pages are not linked automatically: the merchant adds them to the footer links (`/<page-slug>`).

### Pre-launch checklist (before opening signup to the public)
- **Captcha on signup** (Cloudflare Turnstile): the honeypot and timing checks only stop naive bots.
- **Captcha on checkout** too (same widget): orders take stock, and the per-IP limit alone does not stop someone with many IPs from emptying a store with fake orders.
- **Rate limits need the real client IP**: set `advanced.ipAddress.ipAddressHeaders: ["cf-connecting-ip"]` for Better Auth (sign-in limit) and make the VPS accept web traffic only from Cloudflare's ranges, otherwise `cf-connecting-ip` can be forged (`clientIp()` in `src/server/request.ts` is used by our own signup limiter). If the app ever runs as several instances, move `rate-limit.ts` to a shared store.
- **Email**: with no provider, emails are unverified and recovery is manual; decide before a larger launch.
- **Strong secrets**: `BETTER_AUTH_SECRET`, `S3_SECRET_KEY`, database password (the local defaults are for development only).
- **Deleting a company must delete its `tenants/<id>/` files** in storage (there is no delete-company feature yet).
- Add `ROOT_DOMAIN`, `S3_*` and `SIGNUP_*` to the production environment; run the `migrator` before each deploy.
- **Cloudflare IP Geolocation** must be on (it adds the `cf-ipcountry` header used for the default storefront currency).
- **Map:** build the full Cuba archive on the VPS and upload it (see Maps; the local one only covers Havana), and turn on compression for `/api/map/tiles/*` at the edge (Cloudflare or a Traefik compress middleware; tiles leave the app uncompressed and shrink a lot).

### Deployment image
- `Dockerfile` (repo root context) builds `apps/web` with Next `output: "standalone"`; runs `node apps/web/server.js` as non-root on port 3000.
- Build uses **placeholder** `DATABASE_URL` / `BETTER_AUTH_SECRET` only so `next build` can import modules; real values are runtime env vars (`DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `ROOT_DOMAIN`).
- Migrations: separate Dockerfile target `migrator` (`docker build --target migrator -t qvashop-migrate .`), a one-off job that runs `packages/db/src/migrate.ts` against `DATABASE_URL` and exits. Idempotent; run it on every deploy before starting the web app. Locally: `pnpm --filter @qvashop/db migrate:run`.

### Forms and validation
- All forms use **react-hook-form** with a **zod** schema through `zodResolver`, for field-level feedback and flexible validation (refinements, cross-field rules).
- Define each schema once and reuse it on the server (Server Actions / route handlers must re-validate with the same schema; never trust client validation).
- Validation messages are translated: build schemas with a factory that receives the `next-intl` translator, and keep message keys in `es.json` and `en.json`.
- Use the shadcn `Form`/`Field` components with react-hook-form where available, so errors, labels and `aria-*` stay consistent.
- Every form must use `method="post"` and keep its submit button disabled until hydrated (`useHydrated()` from `@/lib/use-hydrated`). Otherwise a submit before hydration is a native GET that puts the fields (including passwords) in the URL.
- Existing forms written with plain state (e.g. login) should be migrated when they are next touched.
- **Every text input and textarea has a placeholder** with a realistic example (`<field>Placeholder` message key, `"Ej.: ..."` / `"E.g. ..."`; a URL slug shows the slug itself, e.g. `sobre-nosotros`). The placeholder is an example, never the label or an instruction (those go in the label / description).
- **Success feedback = a toast** (decided 2026-10): `toast.success(t(...))` from `sonner` (shadcn `sonner` component, one `<Toaster />` in the root layout, so a toast survives `router.push`). Errors stay **inline** (field errors under the field, others in a `role="alert"` paragraph by the form). Messages in the component's namespace under `toasts.*` (older forms reuse their `saved` key). No toast when the change is obvious on screen (reordering, adding an empty banner pair). A Server Action that calls `redirect()` cannot toast (the client code after `await` never runs): return a result and navigate from the client.

### Light / dark theme (decided 2026-10)
- `next-themes` (as in the shadcn docs): `<ThemeProvider attribute="class" defaultTheme="system">` in the root layout toggles the `dark` class on `<html>` (`suppressHydrationWarning` there is required); the choice is kept in `localStorage` per host. `<ModeToggle>` (`src/components/mode-toggle.tsx`) is **one icon button that flips light <-> dark** (sun/moon swapped with CSS, so it is right before hydration); "system" is only the default until the first click, there is no menu to pick it again. It sits in the panel header and in the storefront header (left of the cart).
- Use the semantic tokens (`bg-background`, `text-muted-foreground`, ...) so both themes work; a hard-coded color needs its `dark:` pair. Brand colors (`--brand`) are the same in both themes.

### i18n
- Never hardcode UI text. All strings go in `apps/web/messages/es.json` and `en.json`, with the same keys in both.
- Never put raw `<` or `>` in message strings: next-intl (ICU) parses `<name>` as a rich-text tag and throws `INVALID_MESSAGE`. Pass such text as a placeholder value (`{url}`) instead.
- Use `Link`, `redirect`, `useRouter` from `@/i18n/navigation`, not from `next/link` / `next/navigation`.

## Conventions
